# ML roadmap

Основная соревновательная метрика — ROC-AUC на неизвестных данных без утечек. Задача — бинарная классификация; дообучение LLM не требуется. Эксперименты записываются в [ML_EXPERIMENTS](ML_EXPERIMENTS.md), протокол — в [ML_VALIDATION](ML_VALIDATION.md). После каждого существенного этапа автор выполняет проверки и готовит review package; независимый reviewer проверяет опубликованный Git-снимок; владелец принимает результат и разрешает следующий крупный этап. Правила — в [WORKFLOW](WORKFLOW.md).

Первоначальный [закрытый план ML-1](exec-plans/completed/ML-1.md) объединил аудит, протокол и два baseline в единый контрольный пакет **ML Foundation** (ML-1–ML-3). После независимого R2 и решения владельца он принят. ML-4 tuning прекращён. Прямое задание владельца 2026-10-21 разрешило срочный [ML-DELIVERY](exec-plans/active/ML-DELIVERY.md): inference/submission сейчас, затем текстовый baseline и финальный пакет до 22 октября 10:00 МСК. Прежнее последовательное ожидание ML-5–ML-9 в этом scope отменено.

Последующее прямое задание Quality Improvement Sprint разрешило ограниченные
activity features / CPU XGBoost / малые text OOF blends без новых формальных
этапов. Оно выполнено: [результат](QUALITY_SPRINT_RESULT.md). Существенное
улучшение не подтверждено по предзаданному gate; сохраняется rows65/pkg1.

## Протокол будущих экспериментов ML-4

Для первой серии ML-4 заранее выбраны исследовательские K=100, 500, 1000 на каждый validation fold; они не объявляются согласованной бизнес-ёмкостью. Precision@K и Recall@K вычислять по непрерывному score на валидационных fold; равные score упорядочивать по локальной позиции строки. Распределение score записывать агрегированно по fold; не выбирать параметры по уже просмотренному holdout. Для будущего рабочего процесса K согласовать с владельцем с учётом числа объектов, доступных для проверки. Эти метрики дополняют ROC-AUC и AP, не заменяя их.

Каждый новый запуск получает уникальный `run_id` вида `YYYYMMDDTHHMMSSZ-<случайный суффикс>` и отдельный каталог `artifacts/runs/<run_id>/`. Повторное использование существующего `run_id` запрещено. Baseline CLI поддерживает `--output-dir artifacts/runs --run-id auto` и отклоняет повторное имя; runner ML-4 следует тому же контракту. В каталоге сохраняются конфигурация, seed, хэш источника, версии зависимостей и результаты; журнал ссылается на него. Текущий `artifacts/ml-1/` — унаследованный каталог единственного baseline-запуска.

## ML-8: условия для дополнительных выходов

- `risk_score` — базовый числовой скоринг модели. Для текущих baseline это оценка класса 1 из `predict_proba`, калибровка не проверена; называть её индивидуальной вероятностью нельзя.
- `calibrated_probability` — только после оценки calibration curve и Brier score, обучения калибратора на отдельной части данных и проверки на данных, которые не использовались для его подгонки. Смысл события и горизонт должны быть уточнены.
- `risk_level` (`low`/`medium`/`high`) — только после анализа распределения score и согласования порогов и их интерпретации. Сейчас порогов нет.
- `risk_percentile` — только с фиксированной, описанной референсной популяцией и версией её распределения.
- `top_factors` — исследовать SHAP для подходящей модели; анонимные имена не переводить в несуществующие бытовые показатели и не трактовать вклад в прогноз как причинное влияние.
- Диагностика входа — схема, пропущенные признаки, типы, отсутствие текста, ожидаемые диапазоны и аномалии, если соответствующий метод будет проверен.

Эти компоненты добавляются по подтверждённой пользе и готовности основной модели; ROC-AUC остаётся приоритетом соревнования.

## ML-9: переносимость

Пакет должен включать необходимые модели (весь ансамбль, если он выбран), предобработку, feature schema, Python API, метаданные, закреплённые зависимости, инструкции по установке, нечувствительные контрольные векторы, smoke tests и контрольные суммы. Он загружается без повторного обучения; порядок признаков при обучении и инференсе проверяется. Для закрытого контура документируются версии Python/библиотек, ограничения сериализации, офлайн-установка и сравнение прогнозов после переноса. Экспорт ONNX исследуется на совместимость с фактической моделью и не является обязательным. Перенос во внутренний контур и инфраструктура развёртывания — отдельные согласуемые действия. Проект контракта — в [ML_INTERFACE](ML_INTERFACE.md).
