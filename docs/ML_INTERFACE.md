# Контракт ML-компонента для Backend и Frontend

Статус: **проект контракта**, 2026-10-21. Текущий код обучает и проверяет baseline, но `predict`/`predict_batch` как переносимый публичный API ещё не реализованы. Финальный контракт будет закреплён на ML-9 после выбора модели и независимого ревью. Изменение набора признаков при включении текста потребует новой версии контракта.

## Вход, подтверждённый текущими табличными baseline

Одна запись — словарь с **ровно 1 367 обязательными** ключами `feature_0`, `feature_1`, …, `feature_1366`. Значение каждого ключа — конечное числовое значение, приводимое к `float32` без переполнения. При сборке массива признаки всегда упорядочиваются по сохранённому `schema.json`, а не по порядку ключей словаря. `0` является допустимым значением и автоматически пропуском не считается. Неизвестно, служит ли `-1` кодом пропуска для отдельных признаков; сейчас он не заменяется. Дополнительные ключи внутри `features`, включая `target`, `index` и `word_count`, проектируемый интерфейс отклоняет, чтобы ошибка схемы не оставалась незамеченной.

`index` может передаваться отдельно принимающим приложением как ключ поиска/сопоставления, но не входит в `features` и не влияет на прогноз. Текст пока не входит в табличный baseline. Если ML-5 покажет пользу текста и финальная модель его использует, схему версии ML-9 дополнительно определят фактический формат текстовых частот и поведение при отсутствии текста. До этого нельзя требовать или имитировать текстовый ввод. Все 1 367 столбцов являются предоставленными анонимными числовыми признаками; их смысл и доступность на момент прогноза не подтверждены. Ручную пользовательскую форму на их основе обещать нельзя.

Ориентир Python API:

```python
from typing import Mapping, Sequence, List

predict(features: Mapping[str, float]) -> PredictionResult
predict_batch(records: Sequence[Mapping[str, float]]) -> List[PredictionResult]
```

Это концептуальные сигнатуры, совместимые с аннотациями Python 3.8; окончательные сигнатуры определяются при реализации ML-9. Для пакетного вызова порядок результатов соответствует порядку входных записей. Пакетный вызов может обрабатывать записи частями внутри, не меняя порядок. Сейчас этот код не существует.

Пример **формирования структуры** пакетного входа без персональных данных (нули здесь только иллюстрация схемы, прогноз для них не приводится):

```python
empty_shape = {f"feature_{i}": 0.0 for i in range(1367)}
records = [empty_shape.copy(), empty_shape.copy()]
# После реализации ML-9: results = predict_batch(records)
```

Реальный вход должен содержать рассчитанные признаки объекта. Контрольные векторы для проверки переноса будут подготовлены отдельно и не будут содержать сырые записи людей.

## Предобработка и прогноз

Текущие baseline читают исходные 1 367 столбцов как `float32`, отклоняют NaN/±Inf и не заполняют пропуски. Для SGD Logistic Regression применяется сохранённый `StandardScaler`, обученный только на development. CatBoost получает исходные числовые `float32` признаки. `index` и `target` из массива исключены. Текущие локальные артефакты `artifacts/ml-1/` — экспериментальные, не релизный пакет; `ml.verify` проверяет загрузку и повторяемость прогнозов на контрольных строках. Выбранная финальная предобработка, версия модели и контрольные суммы будут закреплены на ML-9.

## Выход и семантика

`PredictionResult` проектируется как сериализуемая запись с полями ниже. Числа в пользовательском примере дополнения были иллюстративными, не фактическими прогнозами.

| Поле | Тип | Значение и условие заполнения |
| --- | --- | --- |
| `model_version` | `str` | Версия опубликованного пакета; для локальных baseline релизной версии ещё нет |
| `risk_score` | `float` в `[0, 1]` | Основной score для класса `target=1`; у текущих baseline это `predict_proba(X)[:, 1]`, калибровка не подтверждена |
| `calibrated_probability` | `float` в `[0, 1]` или `null` | Только при проверенной калибровке на отдельной выборке и определённом событии/горизонте |
| `risk_level` | `low`/`medium`/`high` или `null` | Только после утверждения порогов |
| `risk_percentile` | `float` в `[0, 100]` или `null` | Только относительно явно указанной референсной популяции и её версии |
| `class_prediction` | `0`/`1` или `null` | Только при заданном пороге классификации |
| `top_factors` | `list` | Вычисленные факторы после проверки объяснимости; пока пустой список |
| `warnings` | `list[str]` | Диагностика принятого входа, например подтверждённое отсутствие доступного текста; пока механизм не реализован |

`risk_score` не является доказанной вероятностью банкротства конкретного человека. В будущем для percentile потребуется документировать референсную популяцию в metadata пакета или самом результате; до этого поле остаётся `null`. Вклад анонимного признака в прогноз не является объяснением жизненной причины банкротства.

## Ошибки и ограничения

Будущий API должен отклонять запись с отсутствующим или лишним ключом, неверным типом, NaN/±Inf или переполнением при приведении к `float32`; ошибка должна указывать имена проблемных полей без вывода всех значений записи. Недоступность файла модели, несовпадение schema/version/checksum и неподдерживаемые версии библиотек должны давать отдельную понятную ошибку загрузки. При пакетном вызове политика ошибок (отклонение всего пакета либо результат на каждую строку) будет определена и проверена перед выпуском.

Диагностика необычных диапазонов, сдвига распределения и отсутствия текста требует подтверждённых правил на реальных данных; сейчас таких правил нет. Нет подтверждения, что все признаки доступны до события. Нет словаря их значений, горизонта целевого события, калибровки или рабочего порога. Поэтому принимающие команды могут проектировать интеграцию по этой схеме, но не должны считать текущие baseline готовым производственным сервисом.
