# Протокол валидации ML Foundation (ML-2 в новой дорожной карте)

Основная метрика — ROC-AUC. Дополнительно измеряются Average Precision (PR-AUC), precision/recall при заранее записанных порогах, train/holdout метрики и время. Accuracy не используется для выбора модели при доле класса 1 около 1,35%.

1. В первых 5 000 строках обнаружены повторяющиеся векторы признаков. Поэтому для baseline зафиксировать `seed=42`: группа — 64-битный хэш всех 1 367 значений `float32`; группы разделить 80/20 с `train_test_split`, стратифицируя группы по наличию хотя бы одной положительной метки. Доли строк/меток после разделения проверить отдельно, они могут немного отличаться от 80/20. Это не доказывает, что совпадающие векторы принадлежат одному человеку, но исключает идентичные входы по обе стороны split. Позиции разбиения сохранять локально. Ни `index`, ни `target` не входят в признаки. TEST не содержит меток и не служит валидацией.
2. Временных меток и идентификаторов субъекта, кроме обезличенного `index`, нет; независимость разных векторов остаётся гипотезой. При обнаружении иных зависимостей пересмотреть разделение до интерпретации метрик.
3. На baseline сравнить модели на одном фиксированном holdout. Для CatBoost early stopping использовать **внутреннее групповое** разделение development (10% групп для остановки, seed=43), затем переобучить на всём development с найденным числом итераций. Holdout для остановки и подбора параметров не использовать. Масштабирование SGD Logistic Regression подгонять только на development. В исходных данных нефинитных значений нет; baseline отклоняет их при подготовке кеша и должен отклонять при инференсе.
4. В последующих оптимизациях использовать групповые разбиения внутри development с учётом дисбаланса классов, например `StratifiedGroupKFold` при приемлемой стоимости вычислений. Обычный `StratifiedKFold` разделил бы одинаковые векторы между fold. Один и тот же holdout не использовать многократно для выбора параметров. Для текста словарь, IDF, отбор и другие статистики вычислять только на train fold.
5. Пороги 0,5 и 0,1 — диагностические, не оптимизированные на holdout. После выбора финальной конфигурации сделать одну оценку на holdout; если baseline holdout уже использован для сравнения, его оценку считать разведочной, а финальную независимую оценку планировать отдельно.
6. Перед выдачей числа как вероятности отдельно проверить калибровку на данных, не использованных для обучения/подбора. Калибровку нельзя оценивать на тех же строках, на которых она обучалась.

Реализация и фактические ограничения должны соответствовать этому документу; любое отклонение записывать в [ML_EXPERIMENTS.md](ML_EXPERIMENTS.md).

## Внутренний протокол ML-4

Разбиения строятся **только** среди сохранённых позиций `development` из принятого baseline. Уникальные 64-битные хэши feature vectors распределяются по трём folds через `StratifiedKFold(shuffle=True, random_state=20261021)` со стратификацией по наличию положительного target в группе. Затем каждому validation fold сопоставляются все строки выбранных групп. Это эффективный эквивалент группового разбиения без дорогой итерации `StratifiedGroupKFold` по каждой строке; фактическое число строк и положительных объектов на каждом fold проверяется. Хэш-коллизия теоретически возможна, но привела бы к избыточному объединению групп, а не к разделению одинаковых входов.

Внутри training части каждого fold 10% групп выделяются для early stopping тем же `stratified_group_split`, seed `20261100 + fold_id`. Validation fold не используется для stopping, выбора числа деревьев, построения признаков или отбора признаков. После выбора числа деревьев модель переобучается на всей training части fold; только затем вычисляются train и validation метрики. Все сравниваемые конфигурации используют идентичные сохранённые folds (`folds.npz` и SHA-256 их позиций в каждом run). Внешний holdout не читается runner и не служит для выбора конфигурации. Средние по трём folds описывают внутреннюю оценку; внешний baseline holdout рядом с ними нельзя трактовать как прямое сравнение на одной выборке.

Основная метрика — ROC-AUC, дополнительная — AP. Gap — train минус validation после refit. Диагностические Precision@K/Recall@K фиксированы при K=100, 500, 1000 на validation fold; равные score упорядочиваются по позиции строки в fold. Квантили score по классу — агрегаты, не исходные записи. При малом числе положительных объектов на fold учитывать разброс и не делать вывод о преимуществе по одному fold.

## Ограниченная регуляризация и повторная CV ML-4 (зафиксировано до новых запусков)

Исторический repeat 0 остаётся неизменным (`cv_seed=20261021`, `stop_seed_base=20261100`). Дополнительные repeats 1 и 2 используют соответственно `(20261022, 20261200)` и `(20261023, 20261300)`, по 3 групповых folds каждый. Алгоритм стратификации групп, доля stop 10%, patience 40, model seed 42 и признаки прежние. Это повторная внутренняя CV на том же development, без нового постоянного holdout; её folds зависимы, поэтому стандартное отклонение (`ddof=1`) — описательный разброс, не стандартная ошибка независимых наблюдений.

На repeat 0 запускаются ровно четыре новых preset с максимумом 1000 деревьев: `lightgbm_min500` (`min_child_samples=500`, приближённое ограничение размера листа), `lightgbm_l1l2` (дополнительно L1=1 и L2=20), `lightgbm_rows65` (к предыдущему subsample=0,65 при freq=1), `lightgbm_depth2` (как l1l2, но 4 листа / depth=2, subsample=0,8). Остальные параметры наследуются от исторического `lightgbm_leaves7`. Увеличенный бюджет общий для новых кандидатов; сравнение с историческим победителем не изолирует эффект бюджета. Полного факторного перебора нет.

Кандидат для repeats 1 и 2 выбирается один раз по наибольшему mean validation ROC-AUC на repeat 0 среди четырёх новых preset; AP и меньший gap — критерии разрешения точного равенства. Он и **неизменный** исторический `lightgbm_leaves7` (300 деревьев максимум) оцениваются на одинаковых дополнительных folds. После просмотра repeats новые конфигурации не добавляются. Сопоставлять парные разности ROC-AUC/AP, число выигранных folds, средние по repeat, общий описательный разброс, train/validation gap, positives, время и накопительный RSS процесса. Не объявлять улучшение по одному удачному fold; repeats — проверка устойчивости после внутреннего отбора, а не независимая финальная оценка. Если бюджет 1000 фактически исчерпан, записать ограничение, не расширяя поиск автоматически.

## Срочная поставка и текст (протокол до результатов)

По заданию владельца без нового LightGBM tuning: full-TRAIN rows65 refit с 191 деревом, медианой девяти prior stopping iterations. Качество оценивается по прежней внутренней CV; full-TRAIN fit не создаёт новую независимую оценку. Текст: фиксированный log1p frequency hashing 2**18, L2, отдельный missing indicator; vocabulary/IDF не обучаются. До метрик исключены основы банкрот/несостоят/конкурсн/bankrupt/insolvenc. Это защита от очевидных outcome слов, а не доказательство отсутствия временной утечки.

SGD log_loss, alpha 1e-4, average=True, seed 42, 5 epochs и train-only shuffle, batch 2048. Оценка на тех же rows65 folds repeats 1/2; A загружается и воспроизводит прежние метрики, B обучается только на fold train, C = 0.5 A + 0.5 B на OOF validation predictions, а при отсутствии usable text C=A. Вес заранее фиксирован, stacking/подбора по holdout/leaderboard нет. Критерий устойчивости: оба repeats улучшаются и не менее 5/6 выигранных folds; затем отдельная проверка утечек, переносимости и дедлайна. При провале поставляется tabular.

## Построчная CV для лидерборда (2026-10-21 вечер, Claude)

Проверка структуры split: точный дубликат вектора в TRAIN есть у 7.65% строк TEST при 7.67%, ожидаемых для
случайного построчного разбиения пула TRAIN+TEST (гипергеометрическая оценка по размеру групп); доля TEST во всех
децилях `index` — 0.30. Значит, TEST — случайные **строки**, и повторные снимки сущностей встречаются по обе стороны.
Групповая CV (выше) оценивает обобщение на новые сущности и остаётся валидной для этой цели, но систематически
не видит сигнала повторов, который есть на TEST. Для выбора модели под лидерборд принят протокол:

1. Development, `StratifiedKFold(5, shuffle=True)` **по строкам**; seed 20261024 — разработка, 20261026 — подтверждение
   (предрегистрировано в research-журнале до запуска). Внешний holdout для выбора не используется.
2. Все признаки, зависящие от меток (TE15, совпадения сущностей LK, band-партнёры BP, NB), для validation строятся
   только по fold-train; для строк fold-train — cross-fitting (TE: `row_hash % 5`; LK/BP/для финала: 5 случайных
   построчных подмножеств), в таблицах значений строка не видит своей метки (общий prior TE — с весом ~1/n). Для TEST — по всему TRAIN.
3. 10% stop внутри fold-train, refit на fold-train; финальная модель — фиксированное число деревьев (214).
4. z-константы бленда — label-free статистики самой validation-выборки (для TEST — батч TEST, заморожены).
5. Изменения конфигурации после подтверждения — только по предрегистрированным правилам (|Δ| порог, ≥4/5 побед на
   обоих seed). Оба seed используют один development: это не независимая оценка.

Разведочная проверка на внешнем holdout выполнена один раз после заморозки конфигурации (holdout отделён по группам
векторов → консервативно для признаков сущностей).

Известное ограничение research CV (найдено ревью Codex): TE/LK/BP строились по всему fold-train до разделения fit/stop,
поэтому метки stop-строк входили в признаки fit-строк — это влияет только на выбор числа деревьев при early stopping.
Финальная конфигурация проверена с фиксированными 214 деревьями (без stopping) на внешних folds и кривой 150–450.
Немеченый TEST (дубликаты, распределение `index`) использован для выбора схемы CV; метки TEST не существуют и не использовались.
