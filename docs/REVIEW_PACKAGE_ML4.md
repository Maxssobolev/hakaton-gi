## Цель и критерии

Сравнить табличные модели на одинаковых групповых folds внутри принятого development, проверить фактические параметры LightGBM, провести четыре целевые конфигурации регуляризации и проверить выбранную конфигурацию на двух заранее заданных повторениях CV. Исключить использование внешнего holdout в подборе/остановке, сохранить модели, provenance, метрики и ресурсы, воспроизвести результаты после загрузки. Критерии — в активном плане; полный протокол и правило отбора — [ML_VALIDATION](ML_VALIDATION.md).

Признаки — все 1 367 числовых столбцов, без `index`, `target` и текста. Источник TRAIN SHA-256 `70063b1cad489056102f3452d838b02e3a2dcfd4a1ac1134c90079cc83f14c70`; использован существующий verified cache v2 `artifacts/ml-1/`. Development — 197 960 строк / 2 674 positives. Совпадающие feature vectors целиком остаются в одной группе.

3-fold group CV: repeat 0 `(CV seed, stop seed base)=(20261021,20261100)`, repeat 1 `(20261022,20261200)`, repeat 2 `(20261023,20261300)`. Внутри каждого training fold отдельные 10% групп для stopping; AUC / patience 40, model seed 42, threads 4. После выбора числа деревьев — refit на всём training fold. Validation не участвует в остановке или построении Dataset. Нового постоянного holdout нет; внешний holdout не оценивался. Проверки SHA-256 читают файлы источника/кеша целиком для контроля целостности; модельные срезы и метрики ограничены development.

Четыре новые конфигурации и repeats зафиксированы до обучения в протоколе. После repeat 0 один раз выбран `lightgbm_rows65`; решение до просмотра repeats 1/2 сохранено в `artifacts/ml-4/regularization_selection.json`. После дополнительных repeats конфигурации не добавлялись. Каждое обучение получило уникальный run ID; полный список, foldwise ROC-AUC/AP/gap, counts и ресурсы — в [журнале](ML_EXPERIMENTS.md).

У каждого локального run есть `results.json`, `folds.npz`, `runner_snapshot.py` и модели. JSON содержит seed, версии, SHA-256 источника, folds, runner и split helper. Это локальные артефакты; публичный reviewer без них может проверить код и агрегаты, но не самостоятельно воспроизвести обучение на приватных данных.

## Результат аудита параметров

Шесть исторических LightGBM-моделей подтвердили `bagging_fraction=0.8`, **`bagging_freq=1`**, `feature_fraction=0.8`, `feature_fraction_bynode=1`, min data 80, L1 0 / L2 3, `max_depth=-1`; число деревьев совпало с JSON. Root counts около 80% training rows доказывают фактическое применение bagging. У нового rows65 root counts 64,61–65,40%. Игнорируемых параметров в проверенной конфигурации не обнаружено.

Фактический минимум размера листа иногда меньше `min_data_in_leaf`: это приближённое ограничение LightGBM, основанное на Hessian; объяснение и ссылка на документацию 4.5.0 есть в журнале. Историческая остановка подтверждается снимком кода, отдельными сохранёнными позициями и числом деревьев, но её AUC history ранее не сохранялась. У всех **24 новых fold-обучений** history закончилась по best+40 до соответствующего лимита; у новых конфигураций предел 1000 оказался достаточным в рамках этой patience.

Новый кандидат: `lightgbm_rows65`, 7 листьев, depth −1, min child 500, L1 1, L2 20, LR 0,05, feature fraction 0,8, bagging fraction 0,65 / freq 1, максимум 1000 деревьев. Исторический incumbent `lightgbm_leaves7` сохранён без изменений: min child 80, L1 0, L2 3, rows 0,8, максимум 300.

На дополнительных folds выигрыш ROC-AUC в 5/6, в среднем +0,007164; по repeats +0,002553 и +0,011775. С учётом отбора выигрыш в 8/9 folds. AP в среднем не улучшился. Gap уменьшился мало и на отдельных folds вырос; новый кандидат имеет больший SD ROC-AUC. Это преимущество по основной метрике внутри повторной CV, а не доказанная статистическая значимость или независимая финальная оценка.

Рекомендация — сохранить rows65 как основной табличный кандидат и завершать текущий tuning ML-4. Ужесточение min child само по себе снизило ROC-AUC, depth 2 резко снизил gap, но уступил rows65 по ROC-AUC. Оснований расширять перебор нет; после ревью и принятия владельцем разумно отдельно разрешить ML-5 и проверить добавочную пользу текста. ML-5 не начат, ML-4 не закрыт. Веса классов и отбор признаков не исследовались в скорректированной ограниченной серии; финальная модель на всём development не обучалась, inference package не выпускался.

## Ограничения и вопросы reviewer

Проверить отсутствие утечек и соответствие реальных параметров описанию; идентичность folds в каждой паре; корректность stopping/refit; фиксацию выбора до repeats; трактовку AP, gap, SD и изменённого бюджета деревьев; достаточность оснований остановить tuning и выбрать rows65 по основной метрике. Не считать все девять folds независимыми и не объявлять полную независимую финальную оценку: repeats используют один development, repeat 0 участвовал в отборе. Прирост нельзя приписать одному параметру — менялись регуляризация, rows и бюджет.

Разные feature vectors могут принадлежать одному субъекту; времени события и subject ID нет. Неизвестно время формирования признаков. Внешний baseline holdout ранее просмотрен и не даёт чистой финальной оценки; его не трогали в ML-4. Score не проверен на калибровку. Текст, ансамбли, SHAP, backend/frontend, inference package и submission вне текущего scope.

Независимое ML-4 ревью **не проводилось**. Владелец ещё не принял ML-4. Следующее решение — разрешить публикацию фиксированного Git-снимка для отдельного ChatGPT review либо запросить локальные исправления; закрытие этапа и начало ML-5 требуют принятия владельцем.
